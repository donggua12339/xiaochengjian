## 背景

### 1. 产品驱动

`docs/PRODUCT_XUANJIA_TIANYAN.md` 规划天衍 v1.0 含 **T4 DEX 字符串加密**、玄甲 v1.1 含 **X14 用户 DEX 字符串加密**：将开发者自有 APK 的 `classes*.dex` 中字符串字面量（`const-string`）替换为密文 + 解密调用，使 MT/NP 的"一键字符串解密"与静态字符串搜索失效。竞品 ShadowSafety 等将"字符串加密"列为标配，缺失将导致产品竞争力不足。

### 2. 与既有红线的表面冲突

ADR 0077 例外 C 红线明确：

> 不允许:自定义 smali / **修改原 dex 业务逻辑** / 添加非 SDK 组件

ADR 0081 锁 2（内容锁定）明确：

> 注入内容仅为 xcj-auth-sdk 的固定 dex 文件;**不允许自定义 smali,不允许插入非 SDK 逻辑**

天衍 T4 需要修改原 dex 的 `const-string` 指令并插入解密调用，**字面上**触碰上述两条约束。若不写本 ADR 直接实现，即构成"代码推翻 ADR 而未走决策追溯"（违反 CLAUDE.md §10，历史上任工程师因此被纠正）。

### 3. 冲突的本质：合规关切是"语义改变"，而非"字节改变"

逐字审视 0077 / 0081 红线的**立法目的与合规关切**，其禁止的"修改原 dex 业务逻辑 / 自定义 smali"，针对的是**语义改变型修改**：

| 语义改变型修改（红线所禁） | 效果 | 损害 |
|---|---|---|
| 去签名校验 | 令校验函数恒返回 true | 破坏权利人技术保护措施 |
| 破解授权 | 改 license 判断分支 | 侵害著作权人财产权 |
| 脱壳 / dump | 还原被加固的源码 | 侵害著作权 + 避开技术措施 |
| 注入弹窗 / 广告 | 改变交互行为 | 侵害用户 + 权利人 |

而保护性字符串加密是**语义保持型修改**：明文 `const-string "api_key_xxx"` 被替换为 `invoke decrypt([密文 byte[]])`，运行时 `decrypt` 返回的字符串**逐字节等于**原明文。程序的**可观察行为完全不变**——相同输入产生相同输出、相同 API 被调用、相同逻辑分支被执行。唯一改变的是**静态字面量的存储形式**（明文常量池 → 密文数组 + 解密调用）。

**因此保护性混淆不触碰 0077 / 0081 红线的合规关切**：它不改变功能语义、不破坏技术措施、不还原源码、不去除保护——恰恰相反，它**施加**保护。红线的关切是"语义是否被改变"，而非"字节是否被改写"。本 ADR 将这个隐含判据**显式化、形式化、机器可验证化**，作为切割红线的安全刀刃。

## 决策

### 1. 核心原则：语义保持性（Semantic Preservation）

**定义**：一个 DEX 变换 T 是**语义保持的**，当且仅当对任意合法输入，变换前后程序的输入-输出可观察行为等价（behavioral equivalence），且变换不引入、不删除、不修改任何**非字面量表示**的指令。

**形式化判据（v1 字符串加密适用）**：

1. **被改指令集合 ⊆ const-string 指令集合**：变换仅触及 `const-string` / `const-string/jumbo` 指令，不触及任何控制流指令、算术指令、调用指令、字段访问指令。
2. **控制流图（CFG）不变**：除"为承载解密调用而新增的局部指令序列"外，每个方法的 CFG 结构（基本块、边、分支条件）与变换前同构。
3. **方法签名不变**：不增删改任何类、方法、字段的签名与可见性。
4. **字面量往返等价**：对每个被替换的字面量 s，`decrypt(encrypt(s)) == s` 逐字节成立（封装期强制往返测试）。
5. **行为等价抽样**：封装期对混淆前后 dex 做"方法体指令序列 diff"，diff 结果必须**完全落在**"const-string → 密文加载 + 解密调用"这一允许模式内，否则拒绝封装。

判据 1-5 在 Packer 加固模式中**自动机器验证**，任一不满足即返回 `SEMANTIC_PRESERVATION_VIOLATED` 并拒绝封装（与 ADR 0077 三重校验"任一失败即拒绝，无跳过开关"同强度）。

### 2. 在 0077 / 0081 框架内新增"例外 D"

本 ADR **不整体推翻** 0077 / 0081，而是：

- 在 **ADR 0077 例外表**新增**例外 D：保护性混淆（语义保持型 DEX 修改）**；
- 在 **ADR 0081 锁 2** 增加**但书**："锁 2 禁止'修改原 dex 业务逻辑'指禁止语义改变型修改；语义保持型保护性混淆（满足本 ADR §1 判据 1-5 且通过 §3 十二锁）不在锁 2 禁止之列。"

例外 D 与例外 A/B/C 同受三重校验强制约束，且叠加 §3 的保护性混淆专锁。

### 3. 保护性混淆五锁（叠加于 0081 七锁之上，仅加固模式生效）

加固模式 = 0081 七锁 + 本 ADR 五锁 = **十二锁**。任一锁失败即拒绝封装。

| 锁 | 名称 | 约束 | 验证方式 |
|---|---|---|---|
| **锁 8** | 语义保持锁 | 变换必须满足 §1 判据 1-5 | 封装期自动跑 CFG 同构检查 + 字面量往返测试 + 方法体 diff 模式匹配 |
| **锁 9** | 范围白名单锁 | 仅允许 `const-string` → 密文 + 解密调用 一种变换；**禁止**改控制流 / 方法体逻辑 / 类结构 / 字段 | AST/指令级 diff：被改指令集合 ⊆ const-string 指令集合，否则拒绝 |
| **锁 10** | 加固模式显式锁 | 加固模式**默认关闭**；admin-web 必须勾选"启用保护性混淆" + 二次确认 + 签署加固 EULA；不勾选则 Packer 走 0081 纯注入流程，**零原 dex 修改** | 后端校验请求体 `hardenMode=true` 且 EULA 签署记录存在 |
| **锁 11** | 可审计可回退锁 | 封装时生成"混淆映射报告"（原字符串 SHA-256 → 密文位置，**不存明文**）存入审计；保留"无混淆对照构建"以证明语义保持 | `packer_log` 增字段 + 对照构建产物哈希入审计 |
| **锁 12** | 解密逻辑自有锁 | 插入的解密调用**仅指向** xcj-defender-sdk 自有 native 解密函数（玄甲多态 / 天衍 VMP 保护），**不引入第三方解密逻辑** | 内容白名单：解密调用目标 ∈ SDK 导出函数白名单 |

锁 8 / 锁 9 是**比 0081 锁 2 更强的机器可验证约束**：0081 锁 2 靠"注入内容固定白名单"，本 ADR 锁 8/9 靠"语义保持性自动证明"，给律师提供可复核的硬证据。

### 4. v1 适用范围（最小合规面）

**0090 v1 仅授权"字符串字面量加密"一种语义保持变换。**

- ❌ **v1 不做**用户 DEX 的控制流混淆 / 控制流平坦化 / DEX2C / 方法体改写 / 指令替换。
- 理由：控制流变换虽理论语义保持，但机器验证行为等价的成本与误判风险显著高于字面量替换；且 ADR 0073 已将控制流平坦化列为"未来工作"并限定 SDK 自身 Rust 层。用户 DEX 的控制流混淆若需启用，**另立 ADR 0090-v2 + 单独律师预审**，不在本 ADR 授权内。
- 效果：v1 的合规面**最小、最锋利**——律师只需审查"字面量加密是否语义保持"这一窄命题，降低预审难度与风险评级。

**v1 适用对象**：与 0081 一致，**仅未加固自有 APK**（加固 APK 走 ADR 0078 自检，不进入加固封装流程；Packer 检测到加固 so 返回 `HARDENER_DETECTED_REJECT_PACK`）。

### 5. 法律三问（提请律师预审，仿 0081 格式）

#### Q1：刑法 285 第三款"侵入/破坏工具"风险

- **预判**：🟢 低（低于 0081）。
- **论证**：285 第三款规制"专门用于侵入、非法控制计算机信息系统的程序、工具"。保护性混淆**不侵入、不控制、不破坏**任何系统，反而**增强**权利人对自己作品的技术保护；十二锁 + 客户端签名自检（0081 锁 7）将"通用性 / 专门性用于侵入"掐死。其性质更接近"保护工具"而非"侵入工具"，风险**低于** 0081 的"注入鉴权"。
- **硬约束**：律师意见书须写明"保护性混淆属施加技术措施，与避开技术措施方向相反，不落入 285 规制范畴"，并参考 MT/NP 类案做合规水位类比。

#### Q2：著作权法 48 / 条例 24（避开技术措施）风险

- **预判**：🟢 低（不触发）。
- **论证**：48 / 24 规制**避开 / 破坏**他人技术措施。本工具对**自有 APK 施加**加密（施加技术措施），不避开任何既有技术措施 → 48 / 24 不触发。

#### Q3：条例 17 / 285 专门性 / 与 0076 方案 B 兼容性

- **预判**：🟢-🟡（开发者侧低 / 小城笺侧中，靠工具中立性 + 十二锁支撑，与 0081 同水位）。
- **论证**：开发者对自己作品做保护性处理，符合条例 17 精神（合法使用者为保护 / 改进作品的必要处理）；小城笺作为工具方，由"自有 + 十二锁 + 客户端签名自检 + 语义保持性机器证明"支撑工具中立性，与 0081 同属"蓝方-自有"安全域。0076 方案 B 禁的是"通用红方"，本 ADR 的十二锁 + 语义保持锁已将通用性掐死，与 0076 "切割通用注入"原则不冲突。
- **回应口径**（律师写进意见书）："0090 是 0081 '自有'安全域内、在语义保持性约束下的有限扩展；保护性混淆不改变程序语义，与 0077/0081 红线的合规关切（语义改变型修改）正交，风险等级不高于 0081。"

### 6. 风险熔断

**若律师评估保护性混淆风险不可控，则自动回退，不强行推进。**

回退条件（任一满足即触发）：
1. 律师认为语义保持型混淆仍不能排除 285 / 48 / 24 风险；
2. 律师认为 §1 的语义保持性判据不足以作为切割红线的依据；
3. 律师认为与 0076 方案 B / 0077 / 0081 不兼容；
4. 律师建议不推进用户 DEX 修改。

回退后：
- 0090 状态改为 `rejected`；
- ADR 0077 例外 D 删除、ADR 0081 锁 2 但书删除；
- 天衍 T4 / 玄甲 X14 **下线**；
- **安全落点**：玄甲 v1.0 基线（仅加密 SDK 自身字符串，路径 1，**不碰用户 DEX**）天然不受影响，产品线仍可发布（天衍以"加固引擎 = 藏 SO + 自实现 Linker + VMP + 托管方案 C"为卖点，不含用户 DEX 字符串加密）。

### 7. 禁止变体（红线，与 0077 同强度）

- ❌ 用混淆管线做去签名校验 / 破解授权 / 脱壳（语义改变型，本 ADR 不授权）
- ❌ v1 修改任何非 `const-string` 指令（违反锁 9）
- ❌ v1 做控制流混淆 / DEX2C / 方法体改写（违反 §4，需另立 ADR）
- ❌ 引入第三方解密逻辑（违反锁 12）
- ❌ 默认开启加固模式 / 无 EULA 签署即加固（违反锁 10）
- ❌ 跳过语义保持性验证（违反锁 8，与三重校验"无跳过开关"同强度）
- ❌ 处理非自有 / 加固 APK（违反 0081 锁 1 + v1 适用范围）

## 备选方案

| 方案 | 说明 | 不选原因 |
|---|---|---|
| A. 不做用户 DEX 加密（玄甲 v1.0 基线） | 仅加密 SDK 自身字符串 | 产品竞争力不足，竞品标配缺失 |
| B. 直接实现 T4 不写 ADR | 快 | 违反 CLAUDE.md §10 决策追溯，历史违规已被纠正，禁止 |
| C. 整体 supersede 0077/0081 | 重写红线 | 灾难性：会动摇三重校验体系，且无必要 |
| **D. 部分修订 + 语义保持锁（本方案）** | 新增例外 D + 十二锁 + 机器验证语义保持 | 合规面最小、论证最锋利、有安全回退落点 |

## 影响

### 正面影响

- 为天衍 T4 / 玄甲 X14 提供合规前提，补全竞品对标矩阵的"字符串加密"项；
- 将"语义保持性"形式化、机器可验证化，形成可复用合规范式（未来控制流混淆 ADR 可继承）；
- 十二锁 + 语义保持锁比 0081 锁 2 提供更强的可复核证据，利于律师预审。

### 负面影响

- 开发成本：Packer 加固模式管线（baksmali → const-string 扫描 → 加密 → 解密调用插入 → smali 回编 → 语义保持性验证）约 5 天（天衍 T4 工程量）；
- 合规成本：需知识产权律师预审 + 加固 EULA 起草；
- 体验门槛：加固模式需用户主动勾选 + 二次确认 + 签 EULA。

### 风险

- **语义保持性验证误判**：自动验证可能漏判某些非语义保持变换 → 缓解：v1 仅允许一种变换模式（const-string → 密文+解密），模式匹配空间极小，误判概率低；辅以"无混淆对照构建"人工抽检。
- **解密调用插入破坏 dex 校验**：插入指令可能改变方法 `code_item` 大小 / 寄存器数 → 缓解：smali 回编后跑 dexlib2 校验 + ART 加载冒烟测试；封装期验证失败即拒绝。
- **律师否决**：→ 触发 §6 风险熔断，回退玄甲 v1.0 基线，无产品断档。
