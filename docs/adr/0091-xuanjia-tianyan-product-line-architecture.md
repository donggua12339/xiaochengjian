# ADR 0091 · 玄甲 / 天衍 加固产品线架构

- 状态:**accepted**（产品/技术架构决策定稿，2026-07-24；玄甲 v1.0 / 天衍 v1.0 代码按路线图实现中/待实现。涉及"修改用户 DEX"的天衍 T4 / 玄甲 X14 槽位**以 ADR 0090 accepted 为生效前提**，0090 通过前该槽位不得启用）
- 日期:2026-07-24
- 决策者:小城笺项目
- 层次:战略 / 功能 / 安全
- 关联产品文档:`docs/PRODUCT_XUANJIA_TIANYAN.md`（本 ADR 是其架构级 ADR 映射；功能清单、对标矩阵、工程量以该文档为准，本 ADR 不重复罗列，仅定义架构边界与决策）
- 勘误(2026-07-24):§3.2 原写"XOR/ROL/ADD/SUB"四原语，经 X1 引擎实现与 C↔py 交叉验证确认为 **XOR/ROL/ADD/MUL**（ADD/SUB 互逆会致相邻排列坍缩为恒等，改用 MUL 乘法原语 + 非退化参数映射，保证 24 排列彼此不同、亿级多态空间）。此为技术事实勘误，不改变本 ADR 的产品线架构决策，故不另开 ADR；产品文档对应处（X1/路径 1/对标矩阵）已同步对齐。

## 背景

### 1. 产品分线需求

defender-sdk（ADR 0088）+ 加固引擎 v0.1-v0.3（ADR 0089：SO 中藏 SO + 自实现 Linker + VMP）已具备完整蓝方防护能力。现需将其组织为**两条产品线**，对标竞品 ShadowSafety 等（见产品文档 §9 对标矩阵），并区分开源免费与付费高级的商业边界：

- **玄甲（XuanJia）**：开源免费加固 SDK，防护功能完整 + SO 加密 + 五层反动态分析；
- **天衍（TianYan）**：付费高级加固引擎，在玄甲基础上叠加"迷宫层"（自实现 Linker + VMP + 字符串分段散列）+ 业务层（用户 DEX 加密 + 托管方案 C + 绕过演练）。

### 2. 必须解决的架构问题

1. 玄甲与天衍**共享哪些、差异哪些**——避免"玄甲是残缺版"的误读，明确二者是**强度分级**而非能力残缺；
2. **玄甲 SO 必须加密**——否则玄甲明文 .so 成为攻击者分析天衍的样本（用户决策）；
3. **玄甲反动态分析必须周全**——采用五层纵深 + SMC，与天衍"迷宫"形成哲学差异（用户决策）；
4. **字符串加密分层**——玄甲 = 多态（路径 1），天衍 = 多态 + VMP + 分段散列（路径 2+3）（用户决策）；
5. Packer 需支持**双模式**（注入模式 / 加固模式），且加固模式的合规闸门指向 ADR 0090；
6. 澄清与 ADR 0061 / 0073 混淆策略的**作用对象差异**，避免后人误判为重复或矛盾。

## 决策

### 1. 产品线功能边界

完整功能清单、玄甲 v1.0（X0-X9）/ 天衍 v1.0 增量（T1-T6）/ 远期 v1.1、工程量、对标矩阵、差异化优势，**以 `docs/PRODUCT_XUANJIA_TIANYAN.md` 为唯一权威**，本 ADR 不复制，仅锁定以下架构级边界：

| 边界 | 玄甲 | 天衍 |
|---|---|---|
| SO 是否加密 | ✅ RC4 + memfd 加载（X0） | ✅ RC4 + 自实现 Linker（T1） |
| 反动态分析 | ✅ 五层防护 + SMC（X4） | ✅ 五层防护 + SMC + 迷宫（自实现 Linker + VMP） |
| 字符串加密（SDK 自身） | 路径 1 多态（X1） | 路径 2+3（T2 + T3） |
| 字符串加密（用户 DEX） | ❌ v1.0；v1.1 经 0090 | ✅ T4（**前置 0090 accepted**） |
| 自实现 Linker / VMP | ❌ | ✅（T1 / T2） |
| 托管方案 C + 绕过演练 | ❌ | ✅（v1.1 T10） |
| 开源 | SDK 开源 | 加固引擎闭源 |

**核心定位**：玄甲 = "门禁 + 陷阱"（五层防护让攻击者走不到 dump 那一步，走到也踩 SMC）；天衍 = "迷宫"（即使 dump 了内存，拿到错乱 ELF + 不可读 VM 字节码）。二者**共享五层 + SMC**（周全），天衍叠加迷宫层（极致）。

### 2. Packer 双模式

| 模式 | 触发 | 原 dex 修改 | 合规依据 | 适用产品 |
|---|---|---|---|---|
| **注入模式** | 默认 | 零（仅 0081 例外 C：注入固定 dex + 改 superclass + Manifest 委托） | ADR 0081（accepted） | 玄甲默认 + 天衍基础 |
| **加固模式** | 用户显式勾选 + 二次确认 + 签加固 EULA（锁 10） | 语义保持型（仅 const-string 加密，v1） | ADR 0081 + **ADR 0090**（proposed） | 天衍 T4 / 玄甲 v1.1 X14 |

- 加固模式在 0090 accepted 前**不得启用**（Packer 后端对 `hardenMode=true` 请求返回 `HARDEN_MODE_NOT_AUTHORIZED`）；
- 注入模式下，玄甲的 SO 加密（X0）+ 字符串多态（X1）在**编译期 / SDK 构建期**完成，**不在 Packer 修改用户 dex**，故注入模式不触发 0090。

### 3. 三条技术管线

#### 3.1 SO 加密管线

| 阶段 | 玄甲 | 天衍 |
|---|---|---|
| 构建期 | RC4 加密 `libxcj_defender.so` → `assets/xcj_enc.bin`；`extractNativeLibs=false` | 同左 + 内层 inner .so 加密（ADR 0089） |
| 加载期 | native 解密 → `memfd_create` → `android_dlopen_ext(ANDROID_DLEXT_USE_LIBRARY_FD)` | native 解密 → **自实现 Linker** 内存加载（不走系统 dlopen） |
| 加载后 | `memset` 清零密文 + 密钥 | 同左 + inner 解密数据清零 |

#### 3.2 字符串加密管线

| 层 | 玄甲 | 天衍 |
|---|---|---|
| SDK 自身 C 字符串 | 路径 1：构建期多态（XOR/ROL/ADD/MUL 四原语 × 24 排列 × per-string seed；亿级多态空间；SBOX 查表作 v1.1 非线性增强） | 路径 1 + 解密函数 VMP（路径 2）+ 分段散列（路径 3） |
| SDK 自身 Rust 字符串 | ADR 0061 obfstr（既有，作用于 xcj-core） | 同左 |
| 用户 DEX 字符串 | ❌ v1.0 | 路径经 0090（baksmali → const-string 加密 → 解密调用插入 → 语义保持性验证） |

**多态对抗 MT 一键解密的原理**：MT/NP 一键解密是**静态**扫描 `.rodata` 用已知算法模板（单 XOR / 单 ADD / base64…）匹配；本管线使 `.rodata` 无明文、且每字符串密文由不同原语排列+seed 复合，模板匹配全部失败。玄甲 SDK 虽开源 decode 算法，但每开发者构建产物的 seed/variant/密文随机生成、不在开源仓库；MT 作为通用工具不读 SDK 源码做针对性提取，故目标达成。对"能读源码的专业逆向"，玄甲靠五层反动态+SMC 挡，字符串算法本身不承担该层（天衍 VMP 的职责）。

#### 3.3 反动态分析五层管线

玄甲与天衍**共享** L1 反注入 / L2 反调试 / L3 反 dump / L4 运行时完整性 / L5 SMC（详见产品文档 §4）。天衍额外以"自实现 Linker 使 dump 后 ELF 结构错乱 + VMP 使 dump 后指令不可读"补足玄甲的诚实边界。

### 4. 与 ADR 0061 / 0073 的作用对象澄清（防误判）

| 混淆能力 | 作用对象 | 源码语言 / 产物 | 技术 | ADR |
|---|---|---|---|---|
| 字符串混淆 obfstr | **xcj-core**（卡密鉴权核心） | Rust / libxcj_core | 编译期 proc-macro，单一算法 | 0061 |
| 字符串多态 X1 | **xcj-defender-sdk**（防守内核） | C / libxcj_defender | 构建期脚本，多态 | 本 ADR（玄甲） |
| 控制流平坦化 | **xcj-core**（SDK 自身，未来） | Rust | proc-macro（方案 C） | 0073 |
| 用户 DEX 控制流混淆 | **用户 APK**（未来，另立 ADR） | smali | 待 0090-v2 | （未立） |

**结论**：0061 与本 ADR X1 **作用对象不同**（不同 crate / 不同 .so / 不同防护目标），是**分层叠加**而非重复；0073 与本 ADR 用户 DEX 混淆**作用对象不同**（SDK 自身 vs 用户 APK），不冲突。后人不得以"已有 0061 字符串混淆"为由否定 X1，也不得以"X1 已做字符串加密"为由跳过 0061。

### 5. 开源边界

- **玄甲 SDK 开源**：defender-sdk 源码 + 玄甲构建脚本开源（与 ADR 0041 SaaS/开源边界、ADR 0040 开源时机一致）；
- **天衍加固引擎闭源**：自实现 Linker / VMP 引擎 / 字符串分段散列 / 加固模式管线作为付费增值闭源（与 ADR 0042 安全设计公开边界"架构公开 + 实现保留"一致：天衍的**架构**在 ADR 0089 / 0091 / 产品文档公开，**实现**保留）；
- 玄甲开源不削弱天衍：玄甲无自实现 Linker / VMP，攻击者从玄甲源码得不到天衍的迷宫层实现。

### 6. 定价

具体价格档位**留商业决策**，本 ADR 不编造数字，仅占位引用 ADR 0043 / 0047 定价框架：玄甲 = 免费；天衍 = 付费（月付 / 年付 / 按次，待定）。会员获利规模遵守 0081 律师硬约束 3（控档，具体数额以司法解释最新版为准）。

### 7. 决策记录（收敛过程，引自产品文档 §14）

1. 产品分界线 = 方案 A+B 混合；
2. 玄甲 SO 必须加密（防成为天衍分析样本）；
3. 玄甲反动态分析必须周全（五层 + SMC，门禁哲学）；
4. 字符串加密：玄甲 = 路径 1，天衍 = 路径 2+3；
5. 玄甲 v1.0 不修改用户 DEX（守 0077），用户 DEX 加密 = 天衍 T4（经 0090）。

## 备选方案

| 方案 | 说明 | 不选原因 |
|---|---|---|
| A. 单产品线 | 不区分玄甲/天衍 | 无法兼顾开源精神与付费增值，竞品对标缺位 |
| B. 玄甲不加密 SO | 玄甲明文 .so | 明文 .so 成为天衍攻击者的分析样本（用户否决） |
| C. 玄甲反动态打折 | 玄甲不做五层 | 用户要求"周全"，玄甲与天衍应是强度分级非能力残缺 |
| **D. 双产品线 + 玄甲周全 + 天衍迷宫（本方案）** | 共享五层+SMC，天衍叠加迷宫+业务层 | 满足开源+付费+周全+对标 |

## 影响

### 正面影响

- 产品线边界清晰，开源/付费分流，对标竞品 32 项有明确补全路径；
- 玄甲 SO 加密 + 五层反动态，杜绝"玄甲喂料天衍攻击者"；
- 与 0061 / 0073 作用对象澄清，避免架构误判；
- 加固模式合规闸门统一指向 0090，决策追溯闭环。

### 负面影响

- 玄甲 v1.0 工程量约 17 天、天衍 v1.0 增量约 13 天（详见产品文档 §12 路线图）；
- 双模式 Packer 增加维护面；
- 天衍闭源部分需持续的"架构公开/实现保留"边界管控。

### 风险

- **路线图延期**：→ 缓解：玄甲 v1.0 P0 先行，天衍依赖玄甲基线，可分阶段发布；
- **0090 律师否决**：→ 天衍 T4 / 玄甲 X14 下线，天衍以"加固引擎（藏 SO + Linker + VMP + 托管方案 C）"为卖点仍成立，无产品断档（与 0090 §6 安全落点一致）；
- **玄甲开源后被 fork 做进攻工具**：→ 缓解：玄甲为纯蓝方防护代码，不含通用去签/脱壳能力，与 ADR 0076 切割通用红方一致。
