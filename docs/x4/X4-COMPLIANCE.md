# 玄甲 X4 · 合规自检报告

> 日期:2026-07-24
> 范围:X4 五层反动态分析引擎的技术调研与实施方案
> 合规边界:ADR 0077(红方能力限定)+ ADR 0091 §X4(五层定义)+ CLAUDE.md §2 守城军规

---

## 1. 调研用途自检

| 检查项 | 结论 |
|---|---|
| 所有调研是否仅用于设计防守能力? | ✅ 是。六来源(看雪/吾爱破解/MT/MT官方/NP/CSDN)文章均从"攻击者如何绕过"反向萃取"我们如何检测/阻断",全部转译为防守侧检测点(L1-L5)。 |
| 是否产出通用去签/脱壳/注入工具? | ✅ 否。调研记录仅含机制级描述(函数名/syscall 号/检测点/魔数),**未保留任何可运行的去签/脱壳/Frida 绕过脚本**。 |
| 攻击代码是否进入玄甲代码库? | ✅ 否。所有调研文章的攻击侧代码(killPM/killOpen/Florida 魔改 frida/Arm64Writer 写 RET/dump 匿名段等)明确标注"严禁照搬",玄甲仅独立重写检测侧。 |
| 是否仅处理开发者自有 APK? | ✅ 是。X4 全部检测点用于保护开发者**自有 APK** 的运行时完整性,不对他人 APK 做任何操作。 |

## 2. 守城军规对照(CLAUDE.md §2)

| 军规 | X4 对照 |
|---|---|
| Ⅰ 禁止通用脱壳 | ✅ X4 是**反脱壳**(L3 反 dump),不拆解任何第三方加固;对商业加固的分析(如 libDexHelper.so)仅为理解威胁模型。 |
| Ⅱ 禁止非授权重打包 | ✅ X4 不篡改任何 APK;签名校验(L4)仅校验自有 APK 完整性。 |
| Ⅲ 禁止越界操作 | ✅ X4 审计能力仅用于自有资产安全排查;不对外提供可复用逆向中间产物。 |
| Ⅳ 禁止伪装身份 | ✅ X4 不涉及签名替换/伪装;签名校验要求开发者自备合法签名。 |

## 3. ADR 合规边界

- **ADR 0091 §X4 五层定义**(本方案的合规边界):L1 反注入 / L2 反调试 / L3 反内存 Dump / L4 运行时完整性 / L5 SMC。本方案严格在此五层内设计,不扩展到其他能力。
- **ADR 0077 红线**:X4 属"开发者对自有应用做加固/防二次打包"的蓝方能力(✅ 允许项),不涉及"修改用户 DEX"(那是 ADR 0090 范畴,X4 不触碰)。
- **ADR 0090 关系**:X4 的 L5 SMC(运行时解密执行)作用于 SDK **自有 .so**(玄甲自身代码),不修改用户 DEX,故不经 ADR 0090 律师门;若后续 X4 涉及用户 DEX 保护,须另走 ADR 0090 流程。
- **ADR 追溯**:X4 实施前须新建 ADR(暂定 ADR 0093《玄甲 X4 五层反动态分析引擎》),记录五层检测点选型与威胁模型上限,纳入 CLAUDE.md §10 决策追溯。

## 4. 威胁模型与能力边界声明(不承诺 100%)

- Android 反动态对抗**没有绝对**。X4 目标:让一键攻击失效,迫使攻击者升级到手动逆向 + 多工具组合。
- **威胁模型上限**(超出用户态防线,方案中已明示):root + 改系统 server 端 / 禁用系统签名验证安装 / 修改内核 syscall table。
- 远期方向:TEE 硬件信任根(用户态防 hook + TEE 二层架构)。

## 6. 风险提示与处置

- 调研中接触的通用攻击工具(MT/NP/ARMPro/Modex/Florida/apksignaturekiller)**仅作为威胁模型与检测指纹来源**,玄甲可提取其**发布特征**(注入类名 `PmsHookApplication`/`HookApplication`、Base64 签名常量格式)作为检测指纹库,**不复用其代码逻辑**。
- 所有防守实现由玄甲团队基于调研机制**独立重写**,做混淆 + native 化 + 多处变形,避免公开标准实现被针对性绕过。

## 7. 结论

✅ X4 调研与实施方案**合规**:仅用于设计自有 APK 的防守能力,不产出通用攻击工具,不照搬攻击代码,符合 ADR 0077 红线与守城军规,在 ADR 0091 §X4 五层定义边界内。实施前须新建 ADR 0093 纳入决策追溯。
